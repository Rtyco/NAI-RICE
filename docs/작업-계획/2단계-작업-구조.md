# 2단계: 생성 작업 구조 바꾸기 (완료)

기록용입니다. 화면 변화 없는 내부 공사였고, 앱 동작은 1단계 후와 같습니다. 3단계 이후에 필요한 현재 구조는
[3단계 파일](3단계-일반-생성.md)의 "지금 구조"에 요약해 두었습니다.

## 계획

- 생성 작업에 종류를 붙입니다: `kind: 'inpaint' | 'txt2img' | 'img2img' | 'augment'`.
- 요청 생성 함수를 종류별로 나누고 공통 부분(V4 프롬프트 구조, 태그 힌트, 샘플러)은 함께 씁니다.
- `GenerationOutput`은 `inpaint`만 자르고, 나머지는 받은 이미지를 그대로 저장합니다.
- `GenerationRecord`에 `kind`, `sourceRecordId`, `anlasEstimate`를 추가합니다.
- **호환:** `kind`가 없는 옛 데이터는 `inpaint`로 읽고, 그 테스트를 추가합니다.

## 결과

- **작업 타입:** `GenerationJobSnapshot`은 공통 필드에 `kind`가 붙는 합 타입입니다(`InpaintJobSnapshot`,
  `Txt2ImgJobSnapshot`, `Img2ImgJobSnapshot`, `AugmentJobSnapshot`). 큐 작업은 `QueuedGenerationJob`입니다.
  - 요청 크기는 모든 종류가 `canvasWidth`·`canvasHeight`를 씁니다. 이름을 바꾸지 않아 옛 큐 파일과 비용
    계산이 그대로 맞습니다.
  - 입력 이미지(`imagePath`·`imageSha256`)는 인페인트·i2i·디렉터 툴에, 마스크·`outputRect`·진단 캔버스는
    인페인트에만 있습니다. 디렉터 툴은 `tool`, `mood`(Emotion), `toolPrompt`, `defry`를 가집니다.
- **요청:** `NovelAIRequestBuilder`의 `buildNovelAIDiffusionRequest`가 일반 생성·i2i·인페인트 본문을 함께
  만들고, 입력 이미지 필드만 다릅니다. `buildNovelAIAugmentRequest`는 디렉터 툴, `buildNovelAIJobRequest`는
  작업 종류에 맞는 주소와 본문을 고릅니다. provider는 작업을 받아 그 주소로 보냅니다.
  - 확인: 인페인트 본문은 바꾸기 전과 모든 모델에서 같습니다. 일반 생성·i2i 본문은 0단계에서 실제로 성공한
    요청과 같습니다(V3, V4, V4.5, V5).
- **모델:** 저장 값(`id`)은 지금처럼 인페인트 모델 ID이고, 모델마다 `requestIds`(인페인트·일반)를 둡니다.
  생성 설정의 모델 선택은 `INPAINT_MODELS`만 보여 줍니다.
- **저장:** 인페인트만 `outputRect`로 자르고, 나머지는 받은 PNG에 메타데이터만 더해 저장합니다.
- **비용:** i2i는 무료 기준을 넘으면 strength를 곱합니다. 디렉터 툴은 배경 제거만 유료로 보고 832×1216의
  65 Anlas에 크기를 비례시켜 대략 추정합니다.
- **호환:** `kind`가 없는 `generations.json` 기록은 zod 기본값으로, 큐 파일의 작업은 `restoreQueuedJob`으로
  인페인트로 읽습니다. 백업 JSON에는 생성 기록이 들어 있지 않아 바꿀 것이 없었습니다. `restoreQueuedJob`은
  옛 로더처럼 `imagePath`만 필수로 봅니다(마스크까지 요구하면 옛 큐 작업이 사라짐).
- **테스트:** 큐 재시도·취소·일시정지와 provider 요청을 실제 `Library`로 시험하는 테스트를 먼저 만들고, 옛 큐
  코드와 새 코드 양쪽에서 통과하는 것을 확인한 뒤 리팩터링했습니다.
- 실험 도구 `entry.ts`도 새 provider 형식에 맞췄습니다.
